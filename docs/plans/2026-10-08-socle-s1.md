# S1 — Projet et conteneurs : plan d'implémentation

## Contexte

Premier lot du socle technique (`docs/plan.md`, bloc 1, S1), validé le 8 octobre 2026. Le dépôt ne contient que la doc et la maquette. S1 pose le squelette sur lequel tout le reste se branche : projet TypeScript outillé (`npm run verify`), Postgres et l'app dans Docker Compose, migrations appliquées au démarrage, page `/health`, CI. **Aucune table métier** : elles arrivent en S3.

Résultat attendu : `docker compose up -d --build`, puis `http://localhost:4300/health` répond `{"status":"ok",...}`. Une PR verte en CI, mergée dans `main`.

### Interfaces

- `loadConfig(env: NodeJS.ProcessEnv): Config` avec `Config = { databaseUrl: string; host: string; port: number; logLevel: 'fatal'|'error'|'warn'|'info'|'debug'|'trace' }`. Valeurs par défaut : `HOST=127.0.0.1`, `PORT=3000`, `LOG_LEVEL=info`. `DATABASE_URL` est obligatoire et doit commencer par `postgres://` ou `postgresql://`.
- `createDb(url: string): { db: NodePgDatabase; pool: pg.Pool }`
- `runMigrations(db: NodePgDatabase): Promise<void>` : idempotent.
- `buildApp(deps: { pool: pg.Pool; version: string; logger?: FastifyServerOptions['logger'] }): FastifyInstance`
- `GET /health` :
  - 200 `{ status: "ok", version, database: "ok", lastBackupAt: null }` ;
  - 503 `{ status: "degraded", version, database: "error", lastBackupAt: null }`.

  `lastBackupAt` est rempli par S2 ; la vérification de la base fait un `select 1`.

## Règle de tests (permanente)

Chaque nouvelle fonctionnalité arrive avec ses tests, écrits avant ou avec le code, et lancés avant chaque commit. Après chaque push sur une PR, les tests sont relancés en local et la CI est suivie jusqu'au vert. Une PR ne se merge jamais avec des tests rouges ou une CI non verte.

## Tâches (un commit par tâche)

0. **Branche, plan et règle** : `git fetch` puis `git switch -c feature/socle-s1 origin/main`. Copier ce plan dans `docs/plans/2026-10-08-socle-s1.md`. Ajouter la règle de tests ci-dessus dans `AGENTS.md`, sous « Vérifier son travail » (hors bloc `coding.md`, pour qu'une resynchronisation ne l'efface pas), puis commit. L'enregistrer aussi en mémoire (feedback). Démarrer Docker Desktop (`open -a Docker`) : le démon est arrêté sur ce poste.
1. **Outillage et configuration** : package.json et scripts, tsconfigs, ESLint, Prettier, Vitest, `.nvmrc`. TDD sur `src/config.ts` :
   - tests : valeurs par défaut appliquées ; `DATABASE_URL` absente → erreur qui nomme la variable ; URL non Postgres → erreur ; `PORT` non numérique → erreur.
   - `npm run verify` passe.
2. **Base et migrations** : `test/postgres.ts`, `test/database.ts`, `src/db.ts`, `src/migrate.ts`, `drizzle.config.ts`, journal vide.
   - Test : sur une base fraîche, `runMigrations` appelée deux fois ne lève rien et crée `drizzle.__drizzle_migrations`.
   - Si drizzle refuse le journal vide : première migration personnalisée minimale via `drizzle-kit generate --custom`.
3. **Santé et serveur** : `src/health.ts`, `src/app.ts`, `src/version.ts`, `src/server.ts`. Tests via `app.inject` :
   - 200 et corps attendu avec la vraie base ;
   - 503 et `database: "error"` avec un pool pointé vers `127.0.0.1:1` ;
   - `version` égale à celle de package.json.
4. **Conteneurs** :
   - `Dockerfile` multi-étapes (build `npm ci` + `tsc` ; exécution `npm ci --omit=dev`, `dist/` + `drizzle/`, `USER node`, `CMD node dist/server.js`) ;
   - `.dockerignore` (node_modules, .env*, secrets, .git, maquettes, docs) ;
   - `compose.yaml` : `db`, avec healthcheck `pg_isready` et volume nommé `db-data` ; `app`, avec `depends_on: service_healthy`, `HOST=0.0.0.0`, healthcheck `node -e fetch(/health)`, `restart: unless-stopped`. Ports sur 127.0.0.1. Mot de passe obligatoire via `${POSTGRES_PASSWORD:?À définir dans .env}`. Le `DATABASE_URL` de l'app est construit dans `compose.yaml`, jamais lu depuis `.env` ;
   - `.env.example` commenté en français, valeurs vides pour les secrets, mot de passe hex recommandé (`openssl rand -hex 24`) ;
   - test de fumée manuel décrit en « Vérification ».
5. **CI et README** :
   - `.github/workflows/ci.yml` sur `pull_request` et `push` vers `main` : `actions/checkout@v7`, `actions/setup-node@v7` (`node-version-file: .nvmrc`, cache npm), `npm ci`, `npm run verify`, `docker build .` ;
   - README, section « Démarrer en local » : prérequis Docker Desktop, `cp .env.example .env`, mot de passe, `docker compose up -d --build`, ouvrir `/health`, arrêter avec `docker compose stop`, et ne jamais lancer `docker compose down -v`.
6. **PR** : push, puis PR vers `main`. Relancer `npm run verify` en local et suivre la CI jusqu'au vert. Revue de code (`/code-review`) et corrections. Après chaque push de correction, on relance les tests et on vérifie la CI. Ensuite, merge et explication à Marc pour tester.

Avant chaque commit : relire `git diff --staged` (données réelles, secrets) et ajouter les fichiers explicitement.

## Risques à surveiller (non couverts par les tests)

1. **Docker Desktop arrêté** : `npm run verify` échoue au démarrage du conteneur de test. Le README le signale en prérequis.
2. **Mot de passe avec caractères spéciaux** : il casse l'URL construite par Compose. On recommande un mot de passe hexadécimal, et `loadConfig` rejette une URL invalide.
3. **Port déjà pris** (4300 ou 5433) : modifiable dans `.env`, documenté.
4. **Base injoignable au démarrage** : l'app s'arrête avec un message clair et `restart: unless-stopped` la relance. En cours de route, `/health` passe à 503 (testé).
5. **`docker compose down -v`** : il efface la base. L'interdiction est rappelée dans le README (et dans `AGENTS.md`).

## Vérification

- `npm run verify` vert sur ce poste (format, lint, types, tests Testcontainers, build).
- Test de fumée :
  - `cp .env.example .env` et renseigner le mot de passe ;
  - `docker compose up -d --build`, puis `docker compose ps` : `db` et `app` passent à `healthy` ;
  - `curl -s http://127.0.0.1:4300/health` répond `status: ok`.
- Résilience : `docker compose stop db`, puis `/health` répond 503 ; `docker compose start db`, puis `/health` répond de nouveau 200.
- Persistance : `docker compose down` puis `up -d` ; le volume `db-data` est toujours là (`docker volume ls`).
- CI GitHub verte sur la PR.
